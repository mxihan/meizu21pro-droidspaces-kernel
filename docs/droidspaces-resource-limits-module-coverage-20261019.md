本报告把源码/声明覆盖与已完成构建分开。找到仓库、Kbuild 输出名或 C 文件，只说明存在候选构建路线，不能证明当前资源限额配置下已经编译、加载或启动成功。

## 工程判断与实际阻碍

源码层面具备继续验证“完整重编”的条件：46 个 manifest 项目目录、BoardConfig 的 39 个外部模块目标都存在；449 个实机模块全部找到 Kbuild 输出声明与至少一个真实候选源码；扫描范围没有 `.o/.ko/.a/.obj/.bin` 预编译内核对象。没有发现已确证的“核心设备驱动只剩闭源 .ko、完全无法重编”的阻碍。仍需保留以下边界：词法覆盖不是完整对象依赖闭包；127 个真实导出未直接命中普通 EXPORT_SYMBOL/qdf_export_symbol 声明，主要为 tracepoint/宏生成符号及 rmnet hook，精确名单在文末，暂记未知。固件、TEE 和厂商用户态服务的开放性没有被本报告验证。

主任务对 `CONFIG_CFS_BANDWIDTH=y` 与 `CONFIG_CGROUP_PIDS=y` 的独立内核构建已经成功，但对照旧实机模块发现 400/449 个模块涉及 core CRC 不匹配，5,317 条导入引用、1,095 个唯一符号受影响，且 cgroup/task_group/cfs_rq/rq 存在物理大小变化。这个结果说明当前已验证的旧模块组合不能被直接沿用到开启限额的新 Image；需要按同一新配置重编配套模块，并独立复核结构布局/CFI/签名保护及实际加载。这里引用的是主任务本轮独立实验结果，本子任务没有重新编译该配置。

当前 cache 仅有 59/449 个同名实机模块的历史编译产物，全部属于 system_dlkm 范围；没有本轮限额配置下全体 vendor 模块成功构建的证据。因此本报告能支持“路线值得继续验证”，不能支持“完整重编已完成”或“刷入即可工作”。新的一整套产物还涉及 vendor_boot 早期模块、vendor_dlkm、system_dlkm 的分区放置、加载列表及一致的签名/打包。

WALT 的 CPU quota 语义需要另行 review 和实际运行测试；有 `cpu.max` 或 CFS_BANDWIDTH 选项不等于当前 WALT 调度路径已经正确执行节流。PIDS 上限也应通过创建进程到达限制的实测验证。

现有 KSU 来自原 init_boot 内的另一个 LKM，不在本报告的 stock 449 个 `.ko` 内。该 LKM 对新内核结构/配置的兼容性、对应源代码/构建版本和重建方式尚未在本子任务确认，必须作为第 450 项之外的独立依赖处理。不能把 449 模块源码覆盖或旧 ABI 报告通过写成“KSU 也会兼容”。
